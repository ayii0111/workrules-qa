# 設計：多輪對話（追問）與輸入防護

> 2026-10-02 定稿。目標是讓 demo 在單人試用時行為穩定、可預期；不設計跨使用者的共用狀態。

## 背景

使用者在聊天介面中會自然地追問，例如先問「平日加班費怎麼算？」再問「那休息日呢？」。
原本的系統只拿最後一句去檢索，第二句單獨看沒有主詞，會找錯資料。

## 資料分類

| 類別 | 內容 | 存放 | 範圍 | 生命週期 | 執行中可否修改 |
|---|---|---|---|---|---|
| ① 知識資料 | 法規、函釋、主管機關說明、工作規則、向量 | SQLite | 唯讀共用 | 每週排程更新 | 唯讀 |
| ② 對話狀態 | 對話紀錄、本分頁最近 60 秒的提問時間、最近失敗的模型與暫停到何時 | `st.session_state` | 只有該分頁 | 「新對話」或重新整理即清空 | 可以 |

執行時會變動的資料，只存在單一 session 中；不同使用者之間互不影響。不儲存使用者的提問內容。

## 每一輪的紀錄（Turn）

| 欄位 | 用途 |
|---|---|
| 顯示文字 | 遮蔽個資後的問題，畫面顯示用 |
| 查詢句 | 改寫後的獨立問題（第一題等於顯示文字），檢索與下一輪改寫用 |
| 回答全文 | 畫面顯示用 |
| 回答摘要 | 結論段前 200 字，只用來給下一輪當脈絡 |
| 引用資料 | 畫面顯示用 |
| 狀態 | ok／refused（拒答）／clarify（需澄清）／blocked（被擋下）／error |
| 系統備註 | 模型降級、改用關鍵字檢索等狀態說明 |

## 處理流程

```
使用者輸入
   │
   ▼
[A] 長度 > 500 字？ ──是──▶ 提示精簡（blocked）
   │
   ▼
[B] 遮蔽個資（身分證、手機、Email）；之後只使用遮蔽後的文字
   │
   ▼
[C] 本分頁最近 60 秒提問次數達上限？ ──是──▶ 提示等待秒數（blocked）
   │
   ▼
[D] 有有效對話紀錄（狀態 ok）？
   │有                                       │沒有
   ▼                                         │
[E] 改寫（輕量模型）                          │
    輸入：最近 2 輪的查詢句 + 新問題            │
   ├─ 指涉不明 ──▶ 請使用者重新描述（clarify）  │
   ├─ 改寫失敗 ──▶ 用原問題，備註降級            │
   ▼                                         ▼
[F] 用查詢句檢索（向量；額度不足時改用關鍵字，備註）
   │
   ▼
[G] 回答（主模型）
    輸入：規則 + 本輪檢索資料 + 最近 2 輪（查詢句 + 回答摘要）+ 本輪問題
   ├─ API 錯誤 ──▶ 依錯誤類型顯示說明（error）
   ▼
[H] 解析引用、產生摘要，存成 Turn（ok 或 refused）
```

## 規則

1. 只有狀態為 ok 的回合會進入下一輪的脈絡；錯誤、被擋下、需澄清的回合只顯示，不傳給 LLM
2. 舊的檢索資料不重送，每輪重新檢索
3. 滑動視窗固定 2 輪，每輪成本固定，不隨對話長度成長
4. 改寫只看查詢句，不看回答全文
5. 個資遮蔽在最前面，之後所有步驟、顯示、紀錄都只使用遮蔽後的文字
6. 知識資料在執行時唯讀

## 使用模式與處理方式

| 使用模式 | 偵測方式 | 處理 |
|---|---|---|
| 同一對話換話題 | 改寫時由 LLM 判斷 | 新問題已完整時原樣保留，不與前文合併 |
| 指涉很久以前的內容 | 改寫時由 LLM 判斷 | 請使用者重新描述 |
| 貼長文 | 字數 | 超過 500 字擋下 |
| 輸入個資 | 正規表達式 | 遮蔽後再處理，並提示使用者 |
| 當律師用（個案勝敗） | 不偵測 | 回答規則：不做個案判斷，引導洽詢人資或勞工局 |
| 反駁、糾正 | 不偵測 | 回答規則：使用者的說法不能當依據，要回頭比對資料 |
| 連續快速提問 | 本分頁的提問時間 | 送出前提示等待秒數 |
| 免費額度用完、服務忙碌 | API 錯誤類型 | 依類型顯示說明（見下） |

## API 狀態顯示

| 狀況 | 辨識 | 顯示 |
|---|---|---|
| 每分鐘額度用完 | 429，訊息含 PerMinute | 請 N 秒後再試 |
| 每日額度用完 | 429，訊息含 PerDay | 今日免費額度已用完，台灣時間下午 3~4 點重置 |
| 主模型忙碌、備用模型成功 | 回應來自非首選模型 | 回答下方備註 |
| 全部模型失敗 | 皆失敗 | Google AI 服務暫時無法使用（非本系統錯誤） |
| 語意檢索額度用完 | 查詢向量失敗 | 回答下方備註「本次改用關鍵字檢索」 |

API key 在 Google 端仍是共用的；他人同時使用造成的超額，不做預測，一律依 Google 回傳的錯誤類型顯示說明。

## 回應速度

- 問答在背景執行緒執行，畫面每 0.2 秒更新各工作階段的讀秒（理解問題、查詢資料、產生回答與使用的模型）
- 回答使用串流：第一個字 25 秒內沒出現視為沒有回應；之後片段間隔超過 25 秒視為卡住；整段 90 秒為總上限。改寫不串流，逾時 15 秒
- 不重試，失敗直接換下一個模型；生成到一半失敗時清掉半段文字，由下一個模型重來
- 模型逾時、忙碌或暫時無法使用後，這個 session 跳過它 5 分鐘；每分鐘額度已滿則跳過到建議的等待時間；每日額度用完跳過 1 小時
- 所有模型都在跳過名單中時，不跳過，仍依序嘗試

## 刻意不做的事

- 跨使用者的額度計數、使用紀錄：demo 以單人試用為主，避免共用狀態造成非預期行為
- 一題多問的拆題：評估尚未證明需要
- 對話紀錄持久化：重新整理即清空，介面上說明
