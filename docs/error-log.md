# 錯誤紀錄

開發過程中實際遇到的問題、原因與處理方式。格式：現象 → 原因 → 處理 → 學到的事。

---

## E1：embedding 免費額度每分鐘 100 筆

- **日期**：2026-09-30
- **現象**：第一次建立 311 條條文的向量時，回傳 `429 RESOURCE_EXHAUSTED`，`quotaValue: 100`
- **原因**：Gemini 免費層的 embedding 每分鐘最多 100 筆，而且一次送 50 筆會算 50 次
- **處理**：
  - 每 90 條一批，每批完成就先寫入資料庫，中斷時已完成的部分不會白做
  - 遇到 429 時等待 62 秒後繼續，最多等 5 次；持續失敗才放棄，並退回關鍵字檢索
  - 實測：等待 3 次、約 4 分鐘後，311 條全部完成
- **學到的事**：使用免費服務前要先查清楚額度，並把「等待後重試」設計進流程，而不是直接失敗

## E2：混合檢索的效果比只用向量差

- **日期**：2026-09-30
- **現象**：18 題評估中，混合檢索前 8 筆命中率 89%，只用向量卻是 100%；「小孩生病需要照顧，可以請什麼假？」「老婆生小孩，先生可以請幾天假？」只有混合檢索找不到
- **原因**：員工的口語提問和條文用詞差異很大，關鍵字檢索找到的多半是雜訊；RRF 對兩邊一視同仁，雜訊就把正確條文擠出前幾名
- **驗證**：把關鍵字權重從 1.0 逐步降到 0，命中率單調上升（MRR 0.75 → 0.97）
- **處理**：預設改為「條號直達 + 向量」，關鍵字只在向量不可用時當備援
- **學到的事**：「業界常見做法」不一定適合手上的資料；先建立評估集，用數字做決定

## E3：月底到職的特休被算成 0 天

- **日期**：2026-09-30
- **現象**：單元測試失敗，8/31 到職的員工在隔年 2/28 應取得 3 天特休，程式卻算出 0 天
- **原因**：計算「滿幾個月」時，只要結束日的日期小於起始日就扣一個月；2 月沒有 31 日，所以 2/28 永遠被判定為「還沒滿」
- **處理**：結束日是該月最後一天時，視為已滿月（參照民法第 121 條第 2 項：以月定期間，最後之月無相當日者，以其月之末日為期間之末日）
- **學到的事**：日期計算的邊界情況很多，這正是試算要交給程式、並且寫測試的原因；如果交給 LLM 計算，這種錯誤很難被發現
- **後續**：2026-10-03 為讓作品聚焦在問答，移除了試算頁面與 `calc.py`（可在 git 歷史中查到）

## E4：參考條文列出太多不相關的內容

- **日期**：2026-09-30
- **現象**：問「特休沒休完怎麼辦」，回答下方列出 8 條參考條文，其中包括請假規則的婚假、病假條文
- **原因**：參考清單直接列出檢索到的前 8 條，但 LLM 只引用了其中 2 條
- **處理**：解析回答中的【勞動基準法 第 38 條】等引用標記，只列出實際引用的條文，順序依照在回答中出現的先後
- **學到的事**：檢索結果是「給 LLM 參考的候選」，不等於「回答的依據」，兩者要分開呈現

## E5：破月薪資問題答不出來，原因不在檢索

- **日期**：2026-10-01
- **現象**：問「月薪三萬，上兩天班後離職／排休兩天再上兩天班後離職……薪資各為何」，系統回答找不到依據
- **排查**：把流程拆成「檢索 → 資料 → 生成」三段檢查。檢索其實有找到相關條文，但**答案不在法條裡**：
  「1 日工資」的算法寫在勞動部函釋，「在職天數包含排休日」寫在臺北市勞動局的說明文章
- **處理**：新增兩種資料來源：精選 20 則勞動部函釋、主管機關說明文章
- **學到的事**：答不好不一定是檢索的問題，要先判斷是哪一段出錯；這題用查詢改寫也救不回來

## E6：提示詞太保守，AI 整題放棄

- **日期**：2026-10-01
- **現象**：補上函釋後，AI 仍然只說「找不到具體規定，建議詢問人資」，連不涉及排休的第一種情境（2,000 元）都沒算
- **原因**：我在提示詞加了「資料沒有明確規定的前提，不可自行假設」，本意是防止編造，結果讓 AI 整題放棄
- **處理**：改成「能確定的先算出來；不確定的列出各種解讀與結果；資料已有評價的解讀作為主要結論」
- **學到的事**：防止幻覺和提供有用的答案之間要取得平衡；規則寫得太嚴，系統就變得沒有用

## E7：說明文章的標題含標點，引用解析失敗

- **日期**：2026-10-01
- **現象**：回答引用了勞動局的說明，但「引用資料」清單卻把所有檢索結果都列出來
- **原因**：解析引用時用頓號、逗號切分多個出處，但文章標題「勞工月中到、離職，當月工資如何計給？」本身就含有頓號和逗號，被切斷後比對失敗，程式就退回列出全部
- **處理**：先把〈〉中的標題整段取出，再切分其餘的出處；補上單元測試

## E8：中英文相連時，個資比對失效

- **日期**：2026-10-02
- **現象**：撰寫個資遮蔽規則時發現，「身分證A123456789」這種寫法比對不到
- **原因**：正規表達式的 `\b`（單字邊界）在 Python 中會把中文字也當成單字字元，中文字和英文字母之間沒有「邊界」
- **處理**：改用「前後不是英數字」的條件判斷邊界；補上中英文相連的測試案例

## E9：評估時查詢向量額度用完，分數可能悄悄失真

- **日期**：2026-10-02
- **現象**：為了讓使用者不用等，提問時的向量計算改成「額度不足就立刻改用關鍵字」。但評估一次要算約 100 個查詢向量，接近每分鐘上限
- **風險**：一旦額度不足，評估會在沒有任何錯誤訊息的情況下改用關鍵字檢索，數字變差卻找不到原因
- **處理**：查詢向量加上快取，同一句話只呼叫一次 API；評估時同一題比較多種檢索方式，呼叫次數減為原本的三分之一。重跑評估，數字與先前一致
- **學到的事**：「自動降級」對使用者友善，但也可能掩蓋問題；評估時要確認自己測到的是想測的東西

## E10：一題要等 1~2 分鐘

- **日期**：2026-10-02
- **現象**：使用者回報「跑很久」
- **排查**：直接測量各模型回應時間：主模型 `gemini-flash-latest` 40 秒沒有回應，輕量模型 0.8 秒；再同時測 9 個模型，發現別名指向的最新版（3.8）逾時，舊一點的 3.5、3.6 只要 4~6 秒
- **原因**：
  1. 外部：免費方案的最新模型最多人用，尖峰時段「不回應」（不是回錯誤，所以只能等到逾時才知道失敗）
  2. 設計：逾時 60 秒，而且會重試一次，要約 2 分鐘才換備用模型
  3. 設計：系統不記得模型剛剛失敗過，每一題都重新等一次
  4. 體驗：畫面只有轉圈圈，看不出卡在哪裡
- **處理**：
  1. 主模型改為指定穩定版本（3.5 → 3.6 → 輕量版保底），被停用時會立刻回 404，不影響速度
  2. 不重試；逾時依用途分開設定：改寫 15 秒、回答 40 秒（實測回答 10~19 秒，太短會誤判）
  3. 模型失敗後，這個 session 先跳過它 5 分鐘（只存在 session，不與其他使用者共用）
  4. 畫面即時顯示每個工作階段與讀秒，回答下方保留完整耗時紀錄
- **結果**：主模型正常時約 10~20 秒；主模型掛掉時，第一題約 40 秒、之後每題回到正常速度
- **學到的事**：「最新版」不等於最適合 demo；外部服務的延遲要量測，而且要讓使用者看得到系統在做什麼

## E11：逾時設計無法區分「沒有回應」與「回答比較長」

- **日期**：2026-10-02
- **現象**：E10 把回答的逾時放寬到 40 秒，理由是「回答長一點要將近 19 秒」。審查時被指出：逾時應該判斷 API 有沒有回應，而不是回答寫多久
- **原因**：非串流呼叫要等模型把整段回答寫完才一次回傳，HTTP 逾時必然包含生成時間。設短了，長回答會被誤判；設長了，真的沒回應時要白等。40 秒只是在錯誤框架下的折衷
- **處理**：回答改用串流，分開判斷：
  - 等「第一個字」：判斷伺服器有沒有在處理
  - 第一個字之後：只要片段持續回來就不算逾時；另設 90 秒總上限防止無限卡住
- **量測後才決定數字**：原本打算「第一個字等 10 秒」，實測完整版模型會先在伺服器內部思考，第一個字 9.5~11.9 秒才出現（輕量版 0.9 秒），片段間隔 ≤ 0.3 秒。若設 10 秒，正常的模型會全部被誤判。最後設 25 秒
- **附帶效果**：回答一邊生成一邊顯示；讀秒拆成「等待回應」與「生成中」兩段，使用者看得懂前 10 秒在做什麼
- **學到的事**：逾時要對準想偵測的事件；數字要量測後再定
